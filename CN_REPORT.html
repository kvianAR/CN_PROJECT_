Extension A — backup DNS

Mac 4 runs a second dnsmasq process with the same project records. Clients list both DNS servers. The backup does not forward project queries to the primary. The local rehearsal stopped the primary process and successfully resolved through the backup. Physical client resolver selection must still be verified after flushing caches, with a packet capture or backup query log.

Learning: DNS availability and application availability are independent. A working cached page does not prove DNS redundancy. Resolver ordering and retry timing depend on the client's resolver.

Extension B — TTL and controlled record change

Both project DNS servers return a TTL of 30 seconds. Records are stored in reloadable hosts files. A separate client dnsmasq cache demonstrates a real cached old answer, a changed source answer, expiry-based refresh and immediate refresh after an explicit flush. All these cases passed in the one-Mac rehearsal using real dnsmasq instances. macOS application cache behavior and flushing remain physical demonstration steps.

Learning: TTL bounds reuse by a compliant DNS cache; it does not terminate existing HTTP/TLS sessions. dig @source observes the source resolver rather than the application's DNS cache. HTTP Cache-Control and DNS TTL control different objects.

Extension C — service isolation

PF rules restrict new inbound backend connections on the configured LAN interface. Strict isolation permits the primary edge source only. During edge migration the standby is explicitly added as another authorized edge. The helper checks the expected local backend role, requires an existing Apple wildcard filter-anchor call, snapshots prior rules, validates proposed rules and loads a dedicated subanchor. It acquires an enable reference only when PF was disabled and preserves a pre-existing enabled state. It restores only its saved anchor/reference. It does not replace the global ruleset or globally disable PF.

Demonstration result: pending on Mac 3 and Mac 4. Both direct-client denial and simultaneous edge access must be recorded with backends running, followed by successful rollback.

Learning: a failed client connection alone does not identify a firewall; a stopped service or wrong route can give the same symptom. Source address, interface, stateful filtering and the actual backend listener must be checked together.

Extension D — backend failure and recovery

Nginx retains passive failure detection (max_fails=1, fail_timeout=5s) and retries eligible GET requests against the remaining upstream. It adds explicit connection source binding, bounded connection/read timeouts and upstream-address/status logging. The local rehearsal observed both A/B, stopped A, observed successful B-only responses, restarted A and observed both again. Both backends down produced HTTP 502 while edge TLS still worked.

Learning: passive health knowledge comes from requests and failures. It is not equivalent to periodic active health probes. Retrying writes can create duplicate effects, so non-idempotent retry is not enabled. A primary edge machine remains a failure point absent an edge recovery plan.

Extension E — controlled edge migration

The standby edge runs on Mac 3 with a separate private key and a server certificate signed by the primary's existing CA. Both edges identify themselves through X-Edge. DNS records on both resolvers are changed to the standby address, while the primary remains available during cache expiry. The local rehearsal validated trusted TLS on both edges and continued standby service after stopping the primary. Its explicit local connection mappings are readiness/rehearsal tests, not proof that real client DNS cutover has occurred.

Demonstration result: natural-domain migration, two-server record consistency and physical client TTL effects remain pending.

Learning: DNS cutover is a controlled recovery procedure with propagation/cache/session timing. It is not automatic zero-interruption edge HA. Backend firewall permissions and TLS trust must be ready before directing clients to the standby.

Extension F — troubleshooting

The diagnostic command records resolver state, independent DNS answers, edge TCP probes, normal HTTPS and explicit-edge HTTPS. An edge-specific mode also probes both backends. The fault table maps observations to DNS, address/port, TLS, proxy, firewall and application checks. The faculty's actual fault, reasoning, fix and post-fix verification must be added during evaluation.

Learning: bypassing one layer can isolate a fault, but a successful bypass is not a successful end-to-end test. State the exact layer tested and return to the ordinary domain path after repair.
